## What this is

Questline: a Next.js 16 (App Router, React 19) app where users track video games on kanban-style boards. Games come from IGDB; checking a game off awards XP (from its IGDB time to beat) and completes the board's streak for the current period. Postgres on Neon via Drizzle, auth via Better Auth, email via Resend.

## Commands

```bash
npm run dev                              # dev server on :3000 (.claude/launch.json entry "dev")
npm run build
npm run lint                             # eslint (next core-web-vitals + typescript)
npm test                                 # vitest watch
npm run test:run                         # vitest once
npx vitest run tests/lib/streak.test.ts  # single file; add -t "<name>" for a single test
npx tsc --noEmit                         # typecheck
npx prettier --write <files>             # 120 cols, double quotes, tailwind class sorting
npx drizzle-kit generate                 # new migration from db/schema.ts into drizzle/
npx drizzle-kit migrate                  # apply migrations to DATABASE_URL
npm run db:seed
```

Env (`.env`): `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `IGDB_CLIENT_ID`, `IGDB_CLIENT_SECRET`, `RESEND_API_KEY`. `db/index.ts` throws at import if `DATABASE_URL` is missing.

## Testing

Vitest + React Testing Library on jsdom, with the `@/` alias. Tests live in `tests/` mirroring the source path, named `*.test.ts(x)`. Server-side suites start with `// @vitest-environment node`; the IGDB client suite mocks requests and credentials. Vitest can't render async Server Components, so cover those end-to-end. Pure logic (streaks, XP math) lives in `lib/` precisely so it can be unit tested without a database.

## Architecture

**Layers.** `app/` holds routes; each feature route colocates `page.tsx` (server component), a client `*Form.tsx`/view, `actions.ts` (server actions), and `schema.ts` (zod schemas shared by client and server). `db/` holds the Drizzle schema plus data-access functions (`db/boards.ts`, `db/experience.ts`, `db/streaks.ts`) that take a `Session` and enforce ownership. `lib/` holds framework-free domain logic and clients. `ui/components` holds shared presentational components.

**Auth.** `lib/auth.ts` configures Better Auth (email/password, mandatory email verification, change email, delete user). Pages call `requireVerifiedSession()` or `redirectIfSignedIn()` from `lib/session.ts`; server actions call `requireVerifiedSession()` and then check ownership via `getOwnedBoard/Group/Card`. `db/auth-schema.ts` is generated by `npx auth generate`; regenerate it, don't hand edit. `nextCookies()` must stay the last Better Auth plugin.

**Server action contract.** Board actions parse input with zod `safeParse` first, then auth, then return `ActionResult<T>` (`{ success, data } | { success, error }`) instead of throwing for expected failures. Board actions deliberately do **not** revalidate: `BoardView` keeps optimistic client state and only calls `router.refresh()` when an action fails, because refreshing re-queries rate-limited IGDB.

**Rate limiting.** `lib/rate-limit.ts` is a Postgres-backed limiter (`rate_limits` table) that checks and increments in one upsert. It's used for auth email/sign-in endpoints (a Better Auth `before` hook in `lib/auth.ts`, which also covers `auth.api` calls from server actions) and per-user IGDB search/lookup budgets (`app/boards/[id]/rate-limits.ts`). IGDB allows 4 req/s app-wide.

**Limits enforced twice.** `MAX_BOARDS_PER_USER`, `MAX_GROUPS_PER_BOARD`, `MAX_CARDS_PER_GROUP` in `db/boards.ts` are checked in app code *and* by triggers in the `enforce_limits` migration (hand-written SQL with its own copy of the numbers and constraint names). Changing a limit means changing both; `isLimitError` maps trigger violations back to user errors.

**Ordering.** Groups ("columns") and cards ("games") have a decimal `rank`. Moves rewrite ranks to `0..n` for the affected lists in a single `db.batch` (neon-http runs a batch as one transaction). Drag and drop uses `@dnd-kit`.

**Streaks and XP.** `lib/streak.ts` is pure: nothing runs when a period ends, so `currentStreak(state, now)` derives the real state from stored fields. `db/streaks.ts` writes with optimistic concurrency (only updates if the stored streak still matches what was read, comparing timestamps at millisecond precision). A card's `streakCounted` flag stops uncheck/recheck from farming streak XP. XP formulas are in `lib/experience.ts`; the client-side total lives in `XpProvider` and pages that change XP push the new total via `useXp().setXp`.

**IGDB.** `lib/igdb-client.ts` wraps IGDB's POST/APICalypse API with Twitch OAuth token caching. Cards store only `gameId`; game details are fetched from IGDB on board load. Box art is served from `images.igdb.com` (allowed in `next.config.ts`).

## Conventions

- Drizzle is v1 RC with relations v2 (`db/relations.ts`, `@better-auth/drizzle-adapter/relations-v2`); APIs differ from older Drizzle docs.
- Zod v4 (`z.int32()`, `z.literal([...])`). String length limits in schemas mirror the `varchar` lengths in `db/schema.ts`.
- Commit messages use Conventional Commits with a scope, e.g. `feat(boards): ...`, `fix(streaks): ...`.
